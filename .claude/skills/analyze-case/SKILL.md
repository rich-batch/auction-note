# analyze-case

특정 경매 사건 하나의 권리관계를 설명하는 글을 쓴다. 입찰 권유가 아니라 **공개 자료로 권리분석을 해 보는 기록**이다. 저장소 구조와 공통 규칙은 루트 `CLAUDE.md`.

핵심 분업: **사실은 사람이 데이터로 넣고, 판정은 코드가 계산하고, AI는 해설만 쓴다.**

| 단계 | 누가 | 무엇 |
|---|---|---|
| 1. 사건 등록 | 사람 | 매각물건명세서·등기사항전부증명서·현황조사서를 보고 `data/cases/<id>.json` 입력 |
| 2. 계산 | 코드 | `node tools/analysis/compute.mjs <id>` → 말소기준권리·인수/소멸·대항력·인수 예상액을 `computed`에 기록 |
| 3. 글 | AI (이 스킬) | 계산 결과를 해설하는 글 초안, `[확인 필요]` 표시 |
| 4. 발행 | 사람 | `[확인 필요]` 해소 → `draft: false` |
| 5. 결과 | 사람 | 매각기일 뒤 `result` 입력 → 글의 매각 결과 표가 다음 빌드에 자동 갱신 |

경로(글 하나 = 사건 ID 하나, 예: `seoul-central-2026ta12345`):

| 무엇 | 경로 |
|---|---|
| 사건 데이터 (사실 + 계산 결과 + 매각 결과) | `data/cases/<id>.json` — 필드 설명 `tools/analysis/README.md` |
| 글 | `content/analysis/<id>/index.md` |
| 조사 노트 (법령 근거) | `pipeline/analysis/research/<id>.md` |
| 검사 | `node tools/check/analysis.mjs content/analysis/<id>/index.md` |

## 링크로 사건 등록

법원경매정보·온비드 같은 물건 페이지 링크를 받으면 **가능한 것만 자동으로 채우고, 서류를 봐야 아는 것은 사람에게 넘긴다** — 등기사항전부증명서·현황조사서·매각물건명세서(공매는 공매재산명세)는 어차피 자동으로 긁어올 수 없다.

**법원경매정보(courtauction.go.kr)**: 자동화된 요청을 탐지해 차단하는 WAF를 운영 중이라(정보통신망법상 접근통제 우회 문제) 자동 조회를 시도하지 않는다. 사건번호·법원·물건종류·소재지·감정가·최저가·매각기일·유찰횟수를 사람에게 직접 받거나(텍스트 또는 화면 캡처), `node tools/analysis/new-case.mjs`로 등록한다.

**온비드(onbid.co.kr)**: WAF 차단이 없고 물건 조회 API가 공개돼 있어 자동 조회가 가능하다. 지금 지원하는 재산유형은 두 가지이고, **법적 근거가 서로 다르므로 자동으로 구분하지 않고 옵션으로 사람이 확정한다.**

| 재산유형 | 법적 근거 | 판정 기준 | 명령 |
|---|---|---|---|
| 압류재산 (기본값) | 국세징수법 제92조 | 등기 접수일 순서(말소기준권리) — court 경매와 같은 구조 | `node tools/analysis/fetch-onbid.mjs <물건관리번호>` |
| 신탁공매 | 신탁법 제4조·제22조 | 신탁등기 접수일 — 등기 소멸/인수는 코드가 판정 안 하고 전부 review | `node tools/analysis/fetch-onbid.mjs <물건관리번호> --type=trust` |

1. **물건관리번호를 받는다** (`2022-0200-007090`처럼 온비드 화면에 보이는 번호 — 온비드는 상세 페이지에 고유 URL이 없어 "링크"가 아니라 이 번호로 찾는다).
2. 위 표에서 재산유형에 맞는 명령을 실행한다. 온비드 화면의 "재산유형" 표시를 보고 고르되, 애매하면(예: 위임기관이 신탁회사인데 온비드 표시는 "기타일반재산") 스크립트가 알려 준다 — `--type` 없이 실행하면 재산유형이 "압류재산"이 아닐 때 위임기관 이름에 "신탁"이 있는지 보고 `--type=trust`를 붙여 다시 실행하라고 안내한다. 그 외(국유재산 등) 유형은 법적 근거를 아직 확인 못 해 사건 파일을 만들지 않고 멈춘다.
3. 이 스크립트가 하는 일(공통):
   - Playwright(Chromium, `npx playwright install chromium`로 최초 1회 설치 필요)로 온비드 물건 검색 API를 호출해 공개 필드(사건번호·물건종류·소재지·면적·감정가·입찰기간·유찰횟수)를 가져온다.
   - 한 물건에 여러 회차(감액되는 최저가)가 동시에 예약돼 있으면 가장 가까운 회차를 자동으로 고른다.
   - 소재지는 온비드 물건명(전체 주소, 지번·동·호수 포함)을 그대로 쓴다 — 법원경매정보·온비드가 법률상 공개하는 정보이고 기존 경매정보 서비스도 동일하게 전체 주소를 쓴다. 사람 이름·주민번호·전화번호는 계속 금지(FORBIDDEN_KEYS·정규식 검사).
   - `data/cases/onbid-<물건관리번호 숫자만>.json`을 만든다. `source.type: "onbid"`, `case.onbid_property_type`은 "압류재산" 또는 "신탁공매".
4. **`rights[]`·`tenants[]`·`spec_sheet`는 여전히 자동으로 못 채운다.** 사람이 등기사항전부증명서·공매재산명세를 보고 채워야 한다 — 스크립트가 끝나면 무엇을 채워야 하는지 목록으로 알려준다. 최저입찰가격이 온비드에서 "비공개"로 표시된 경우 `sale.minimum`도 사람이 채워야 한다. **신탁공매는 추가로 `case.trust_registered_on`(신탁등기 접수일, 등기사항전부증명서에서 확인)도 사람이 채워야 `compute.mjs`가 계산한다** — 없으면 INVALID로 막힌다. 온비드에 첨부 임대차 현황 PDF가 있으면 Playwright로 열어서(팝업을 스크린샷) 참고할 수 있지만, 거기 나온 "임대차 기간"은 전입일이 아니므로 그대로 `tenants[].registered_on`에 쓰지 않는다.
5. **시세 조사(선택)**: 원하면 WebSearch/WebFetch로 네이버부동산·국토교통부 실거래가 공개시스템 등에서 인근 비교 사례 후보를 찾아 제시한다. 이건 그때그때 한 번 찾아보는 리서치이지 자동으로 캐싱·반복 수집하는 배치가 아니다. 사람이 확정한 값만 `market.trades[]`에 넣는다.
6. 이후는 기존 **새 글** 절차와 같다: `compute.mjs` → 글 작성.

## 새 글

1. **계산 최신화.** `node tools/analysis/compute.mjs <id>`. `INVALID`면 멈추고 무엇을 고쳐야 하는지 사람에게 보고한다(데이터를 추측으로 고치지 않는다).
2. **지시문 받기.**
   ```bash
   node .claude/skills/analyze-case/render-prompt.mjs --case <id>
   node .claude/skills/analyze-case/render-prompt.mjs --next 1
   ```
3. `=== JOB` 블록대로 0단계(조사 노트) → 1단계(글) → 2단계(셀프 리뷰) → 검사. FAIL은 PASS까지 고친다.
4. **로컬 확인.** `hugo -D -d <스크래치 폴더>` 빌드가 에러 없이 끝나는지(사건 데이터가 없거나 `computed`가 없으면 shortcode가 빌드를 멈춘다).
5. **보고.** 템플릿의 보고 항목 + 사람이 발행 전 해야 할 일(`[확인 필요]` 해소, 최신 매각물건명세서와 대조).

## 분류(`case.category`)별 차이

| 분류 | 계산 | 글에서 |
|---|---|---|
| apartment · villa · commercial | 아래 권리분석 엔진 그대로 (상가 임차인은 상가건물임대차보호법 규칙) | 표준 구조 |
| land | 같은 엔진, 임차인은 입력 금지(`special`에 기록). 법정지상권·지목/맹지·농지취득자격증명이 review에 자동으로 남는다 | `## 임차인과 점유`는 "점유 현황"으로 쓰고 토지 확인 항목을 `## 입찰 전 확인할 것`에 |
| car | **엔진 없음** — 사건 데이터 검증이 막는다. 첫 자동차 사건이 생길 때 입력 항목·규칙·글 구조를 함께 만든다 | (미정) |

분류 추가: `data/categories.json`에 한 줄 → 분류 페이지·탭·검증에 자동 반영. 계산 방식이 다르면 `engine`을 새로 정의하고 `rights.mjs` 검증을 갈라야 한다.

## 계산 도구가 하는 것 / 못 하는 것

**한다** (`tools/analysis/rights.mjs`, 테스트 `node --test tools/analysis/rights.test.mjs`):
- 말소기준권리: (근)저당권·압류·가압류·담보가등기·경매개시결정 중 가장 빠른 접수(같은 날이면 접수번호), 건물 전부 전세권 + 배당요구
- 등기 권리 인수/소멸: 말소기준권리보다 앞서면 인수, 뒤면 소멸. 선순위 전세권은 배당요구 시 소멸
- 임차인 대항력: 점유(또는 임차권등기) + 전입·사업자등록일이 말소기준권리 접수일보다 **하루 이상 앞설 때**
- 인수 예상액: 대항력 있고 배당요구 안 함 → 보증금 전액 / 배당요구함 → 0 ~ 보증금(배당 순위 미계산)
- 입찰보증금(기본 10%, 재매각 20%), 감정가 대비 최저가 비율
- 매각물건명세서 기재(최선순위 설정, 인수 권리)와 대조해 어긋나면 review

**못 한다 → review로 남김**: 배당표(누가 얼마 배당받는지), 소액임차인 최우선변제, 유치권·법정지상권·분묘기지권, 후순위 가처분의 성격, 가등기의 성격(담보/보전), 대지권 미등기·토지별도등기 등 `special`에 적힌 사항.

규칙을 바꾸거나 추가할 때는 `rights.mjs`와 `rights.test.mjs`를 함께 고치고 테스트를 통과시킨다. 법령 근거를 주석에 남긴다.

## 자주 막히는 곳

| 증상 | 원인 / 해결 |
|---|---|
| 검사 "computed가 오래됨" | 데이터를 고친 뒤 compute를 안 돌림. 다시 돌리고 글이 새 결과와 맞는지 확인 |
| 검사 "사건 데이터에 없는 금액" | 본문에 계산해서 만든 숫자. 데이터 값(또는 두 값의 합·차)으로 바꾸거나 지운다. 필요한 값이면 사람이 데이터에 넣는다 |
| 빌드 에러 "data/cases/…json이 없음" | front matter `case`와 파일 이름이 다름 |
| 시세를 쓰고 싶음 | 사람이 `market.trades`에 실거래 사례와 `source_url`을 넣은 뒤에만 |
| 매각기일이 연기·변경됨 | 사람이 `sale.sale_date`를 고치고 compute 재실행(입력 해시가 바뀜) |
